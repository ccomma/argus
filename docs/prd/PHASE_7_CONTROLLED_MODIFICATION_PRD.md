# Phase 7: 受控修改与回滚机制 PRD

> Context loading: 新会话默认先读 `docs/context/CURRENT_HANDOFF.md`，再按需读取本 PRD。本文件只回答产品问题，不承担实现任务管理。

## 1. Background

Phase 6 的能力解析引擎输出了对能力缺口的处置决策建议（复用、配置、本地创建等）。但要真正执行这些建议——修改一个 skill、更新一份工作契约、调整角色能力包——就需要一个安全的修改管线：改前自动备份、改时记录差异、改后审计留痕、必要时可回滚。

Phase 7 构建的正是这条"快照-差异-审计-回滚"管线。核心原则是：任何持久化行为变更都必须可追踪、可验证、可回滚。

## 2. Users and Jobs

目标用户：

- 需要对本地能力资产或工作契约进行受控修改的开发者。
- 在采纳 Phase 6 的决策建议后，需要安全执行修改而非手动编辑文件的用户。
- 需要事后审查"谁改了什么、为什么改、如何恢复"的治理者。

用户任务：

- 修改前自动捕获资产或合约的完整快照。
- 生成修改前后的结构化差异（unified diff + 字段变更列表）。
- 修改后写入不可变审计日志。
- 从审计记录加载对应快照，执行回滚恢复至修改前状态。
- 生成包含审计日志和差异详情的修改报告。

## 3. Problem

当前问题：

- 对能力资产和工作契约的直接修改没有自动备份机制，改错后难以恢复。
- 缺少结构化的差异记录——用户只能看到文件变了，不知道具体哪些字段、哪些行被改了。
- 修改操作没有不可变审计追踪——事后无法回答"谁在什么时候为什么改了什么东西"。
- 没有从审计记录一键回滚的能力——恢复依赖人工记忆或手动文件版本管理。

## 4. Goals

- 提供不可变的修改前快照（ModificationSnapshot），以内容寻址 ID（SHA1）确保相同内容产生相同标识。
- 提供结构化差异计算（AssetDiff），覆盖能力资产和工作契约两种主体类型。
- 差异以 unified diff 格式输出，同时统计新增/删除行数和变更字段列表。
- 审计日志以追加写入（append-only JSONL）方式存储，确保不可删除和篡改。
- 回滚操作从审计记录加载快照，恢复资产或合约至修改前状态，且回滚本身也产生审计记录。
- 输出 Markdown 和 JSON 双格式修改报告。

## 5. Non-goals

- 不做多版本分支管理（不实现 git 风格的 branch/merge）。
- 不做自动冲突解决——冲突由人工判断。
- 不做实时文件监控或自动触发备份——当前由调用方显式触发。
- 不做团队级修改审批流——当前为单用户本地使用。

## 6. Core User Flows

修改前准备：

1. 调用方（CLI、MCP 或内部服务）触发修改操作前，先通过 SnapshotManager 捕获当前状态的快照。
2. 快照以内容字典序列化为稳定 JSON，基于核心属性 SHA1 哈希生成内容寻址 ID（snap-{16位hex}）。
3. 快照持久化为 {snapshot_id}.json 文件。

执行修改与记录差异：

4. 修改执行后调用方通过 AssetDiffer 生成前后差异。
5. AssetDiffer 将前后对象序列化为排序 JSON，逐行对比生成 unified diff。
6. 同时统计新增/删除行数，并对比字段级差异得出 changed_fields 列表。
7. AssetDiff 以 diff-{16位hex} 作为内容寻址 ID 持久化。

审计记录：

8. 每次修改通过 AuditLedger 追加一条 ModificationAuditRecord（audit-{16位hex}）。
9. 审计记录关联快照 ID、差异 ID，并包含触发者、触发原因、操作类型和回滚指令说明。
10. 审计数据写入 append-only JSONL 文件，不可删除。

回滚流程：

11. 用户通过 RollbackManager 指定一条审计记录执行回滚。
12. RollbackManager 加载审计记录中引用的快照。
13. 根据 subject_type（capability_asset 或 work_contract）选择恢复策略。
14. 恢复完成后生成一条 action="rollback" 的新审计记录，形成完整闭环溯源。

报告输出：

15. ModificationReporter 汇总所有审计记录、快照和差异，输出 Markdown（含 diff 代码块，限 40 行）和 JSON 双格式报告。

## 7. Success Criteria

- 每次 durable behavior change 都有快照、差异和审计记录。
- 修改失败可通过快照恢复至修改前状态。
- 回滚操作本身也产生审计记录，事后可追踪完整修改—回滚链路。
- 审计日志能回答：谁触发、为什么触发、改了什么（关联 diff）、如何恢复（关联 snapshot）。
- 至少支持 capability_asset 和 work_contract 两种主体类型的受控修改与回滚。
- 内容寻址 ID 确保相同内容产生相同标识，支持幂等操作。

## 8. Risks and Open Questions

风险：

- 快照内容为全量字典序列化，大资产或多版本历史可能导致存储膨胀。当前无自动清理策略。
- Unified diff 算法为简化实现，非标准 myers diff——在大差异场景下输出可能不够紧凑。
- 回滚当前仅支持全量恢复（替换整个对象），不支持对特定字段的部分回滚。

开放问题：

- 是否需要快照的自动过期/清理策略（按时间或按版本数上限）？
- 是否应扩展到支持 role pack、question strategy 和 deliverable contract 等更多主体类型？
- 是否需要 preview/apply 两阶段提交模式（当前修改即生效）？
- 回滚是否应支持"回滚到指定快照"而非仅限于"回滚上一次修改"？
