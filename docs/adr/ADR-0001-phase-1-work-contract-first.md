# ADR-0001：Phase 1 先实现工作契约 MVP

## 状态

已接受

## 背景

Argus 的长期目标包含工作契约、自动学习、能力管理、角色组合、治理、审计和回滚。这个范围很大，如果第一阶段直接从能力资产清单、自动安装、角色市场或仪表盘开始，容易把核心用户价值藏在底层系统里。

当前最需要验证的是：中重度 AI 产出者是否真的需要 Argus 主动追问，并把模糊意图转化为可执行、可验收、可复盘的工作契约。

## 决策

Phase 1 先实现本地优先的工作契约 MVP。

第一阶段只做：

- 模糊意图输入。
- 提问策略（question strategy）。
- quick / standard / strict 追问深度。
- 完整度评分（completeness score）。
- 工作契约（work contract）。
- 交付物契约（deliverable contract）。
- 交付物评估器（deliverable evaluator）。
- 最小本地存储和执行证据（execution evidence）。

第一阶段不做：

- 外部能力自动安装。
- skill、MCP、plugin、rule、memory 自动修改。
- 完整能力资产清单。
- 团队后台。
- 仪表盘（dashboard）。
- 大量角色模板。

## 替代方案评估

- 先做 Argus Core 事件账本：能更贴近原始项目，但用户第一眼价值不够显性。
- 先做能力资产清单：能展示本机能力资产，但不能解决用户"不知道如何开始复杂工作"的痛点。
- 先做角色模板库：启动快，但容易退化成 prompt 包，差异化不足。
- 先做团队治理平台：长期价值高，但当前信任、权限、审计和实现成本过高。

## 后果

正面影响：

- MVP 更贴近用户显性痛点。
- 第一阶段边界清晰，避免过早进入高风险自动化。
- 后续 Argus Core 可以从工作契约的执行证据中获得更干净的学习输入。
- 角色、能力包和治理都能围绕同一份工作契约扩展。

代价和风险：

- Phase 1 暂时不能展示完整能力治理野心。
- 完整度评分和交付物评估器早期可能比较启发式。
- 如果工作契约体验不够强，后续能力治理价值会缺少入口。

## 复核触发条件

需要重新审视该决策的情况：

- 工作契约 MVP 无法展示明显用户价值。
- 用户更强烈需要能力资产治理而不是需求澄清。
- 后续能力包和角色组合无法自然接入工作契约。
